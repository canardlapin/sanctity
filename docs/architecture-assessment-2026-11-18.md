> **Status, 19 November 2026.** The findings stand. The recommended order and the delivery map below are superseded by the [plan of record](plan.md): ARC01, ARC02, ARC04, ARC06, ARC07 and PRO04 moved into MVP journeys, and the rest is parked.

**Keep the release model and the single service. Give discovery, custodianship and exchange the same architectural care that acceptance already receives.** A lab can already add a session, review a correction and preserve the earlier state. A finished collection can enter through the same workflow and retain its exact files. The weaker part of the design is what a second person or a second installation can do with that release years later.

## Findings that change the next tranche

### 1. A deposited collection needs a searchable catalog record

The archive descriptor supports title, description, creators, keywords, data types and identifiers. PostgreSQL’s project directory searches the separate, optional placement label. The scientific query takes already identified releases and requires scientific facts. These serve different questions. In the running demo, the steward found the protocol archive by its label. Searching for “fictional lab records,” words present in its readable descriptor, returned no match for that archive. Someone inheriting a collection is precisely the person least likely to know its project label. [Archive fields](../modules/bids/src/main/scala/sanctity/bids/ArchiveInterpreter.scala#L83) · [Directory implementation](../modules/postgres/src/main/scala/sanctity/postgres/PostgresOrganizationCatalog.scala#L80)

**Design change.** Publish a small catalog record for each accepted release, derived from the accepted descriptor and reusable for both BIDS and ordinary archives. Keep the project label for navigation. Decide which fields a discovery-only user may see. Search, snippets, facets and counts must all operate on the caller’s permitted fields and release scope. A grant to R1 must never yield the description from R2. An archive with no scientific index must be findable. A PostgreSQL projection with a reference implementation is sufficient for this job.

**Related defect, reproduced.** Directory cursors hash the ordered IDs but resume from the previous *name and ID*. With a page size of one, renaming the first entry from A to AA before fetching the next page returned the same entry twice. Bind the cursor to the actual ordering keys and test rename, permission change and expiry during paging. [Cursor code](../modules/application/src/main/scala/sanctity/application/Directory.scala#L36)

### 2. Custody and sharing need to work from a fresh browser

The custodian UUID field exposed a gap in the model. Public creation recognizes a custodian by asking whether **any existing dataset already has that UUID**. The schema stores an ID on the dataset. The creation workflow has no named custodian directory from which to choose. The first deposit for a new custodian therefore depends on prior operator setup outside this path. Give the institution a small custodian record with a stable ID, display name and active status. Backfill existing IDs, preserve historical references, and let the form default the sole eligible custodian or show a named choice. [Creation transaction](../modules/postgres/src/main/scala/sanctity/postgres/PostgresOrganizationCatalog.scala#L138) · [Current form](../modules/http/src/main/resources/sanctity/ui/app.js#L421)

The steward’s access screen reads its grant list from browser state even though the service already exposes current grants. The form offers metadata and content reading but cannot issue the explicit discovery permission that puts a release in **Shared with you**. The two-account rehearsal proves access by a known release URL. The recipient finding it from the home screen is a different, currently incomplete journey. Grant creation also mints a fresh ID per HTTP request. If a successful response is lost, a retry can create a second active grant. That last finding follows from the transaction and API code. [Console](../modules/http/src/main/resources/sanctity/ui/app.js#L1646) · [Shared directory rule](../modules/kernel/src/main/scala/sanctity/kernel/OrganizationAuthority.scala#L229) · [Grant writes](../modules/postgres/src/main/scala/sanctity/postgres/PostgresCatalog.scala#L44) · [Browser rehearsal](../tests/console/institutional.js#L45)

**Acceptance test.** The steward chooses whether the share is discoverable. A recipient starting at Home finds exactly the disclosed release when discovery is granted. A steward in a second browser can inspect its scope and expiry, revoke it, and see whether any independent access remains. A retried submission with the same intent key creates one grant. Preserve intentional link-only access as a distinct choice.

### 3. File bytes travel well. The evidence explaining their origin needs a public format

I exported a three-file archive from one reference catalog and admitted it to a second using independent storage. All three file paths, sizes and SHA-256 digests matched. All three directories survived, including an empty one. The local release and manifest IDs changed. This follows directly from the manifest encoding, which includes locally allocated artifact IDs. The current directory export returns counts, bytes and the source manifest ID. The public release reference contains the dataset and release UUIDs. These are sound local records, but a receiving institution still needs to establish what the source disclosed and what it received. [Manifest encoding](../modules/kernel/src/main/scala/sanctity/kernel/Manifest.scala#L63) · [Release and receipt types](../modules/kernel/src/main/scala/sanctity/kernel/Lifecycle.scala#L17) · [Directory export](../modules/objects/src/main/scala/sanctity/objects/DirectoryExport.scala) · [Cross-institution design](design-baseline.md#authority-and-collaboration)

**Design change.** Start with a versioned transfer manifest beside the exported data. Identify the issuing repository and disclosed release or view. List the exact paths, kinds, sizes and content digests, with a portable inventory digest that an independent reader can recompute. Carry only authorized description, provenance and coverage. The receiver verifies the inventory, records its source and accepts under a local custodian and local grants. A restricted subset must disclose only its approved scope. Source revocation governs future source delivery. A copy already accepted elsewhere has a distinct custodian. This contract can be tested offline before choosing a network protocol, trust mechanism or federation service. Keep existing local identities intact.

### 4. The HTTP contract diverges from both the implementation and the console

I compared normalized HTTP method/path pairs in the repository dispatcher with the checked-in OpenAPI document. **19 of 50** implemented `/v1` operations appear in the specification. All 19 are implemented. The 31 omissions include project dataset creation, directories, shared releases, grant listing and reassessment. This count excludes the separate `/auth` routes. I also read a release from the packaged demo. Its `provenance` field is always emitted by the encoder, while the published schema forbids additional properties and omits that field. A validating client can reject a successful release read. [Dispatcher](../modules/http/src/main/scala/sanctity/http/RepositoryHttp.scala#L118) · [Public encoder](../modules/http/src/main/scala/sanctity/http/PublicJson.scala#L62) · [OpenAPI](http-api.openapi.json)

**Acceptance test.** An independent client using only the published contract can discover a collection, inspect a permitted release, receive an authorized file and verify it. Exercise the actual packaged server, validate successful and error responses, and compare supported routes with the contract in CI. Keep public response encoders distinct from database record codecs so historical storage changes do not dictate the external API.

### 5. Current authorization performs institution-wide work for each file chunk

File reads and exports recheck current authority every 64 KiB. In an organization-enabled PostgreSQL catalog, that call reloads principals, releases, datasets, grants and organization records, then evaluates the policy in memory. A 1 GiB file therefore triggers **16,384 chunk checks**, in addition to setup. That is a count derived from the code, not a throughput measurement. Directory pages also load a snapshot containing organization events and processing runs before filtering and paging. Study size and institutional history will both affect ordinary use. [Delivery](../modules/application/src/main/scala/sanctity/application/NativeRepository.scala#L122) · [Authorization path](../modules/postgres/src/main/scala/sanctity/postgres/PostgresCatalog.scala#L563) · [Policy reads](../modules/postgres/src/main/scala/sanctity/postgres/PolicySql.scala#L40) · [Directory snapshot](../modules/postgres/src/main/scala/sanctity/postgres/PostgresOrganizationCatalog.scala#L282)

**Design change.** Keep the pure policy evaluator as the correctness oracle. Measure a download and directory traversal against growing numbers of unrelated datasets, releases and grants. Use a scoped indexed read for the facts contributing to the decision, including credential state, time-based expiry and any upstream source restriction. Maintain the existing mid-stream revocation guarantee. Separately measure browser memory and bytes reread on session addition. The browser buffers a complete file for hashing, admission limits the combined inventory to 10,000 entries, and acceptance verifies every distinct blob in the candidate. Raising the limits alone would magnify these costs. [Upload](../modules/http/src/main/resources/sanctity/ui/upload.js#L73) · [Inventory bound](../modules/application/src/main/scala/sanctity/application/ImportPlan.scala#L11) · [Acceptance verification](../modules/application/src/main/scala/sanctity/application/NativeRepository.scala#L103) · [Existing workload and budgets](engineering-workload.md)

### 6. Make scientific capabilities independently optional

The modality registry is a useful starting point. Today, an assessed modality supplying `ModalityRules` must also supply a view compiler, and the service registers a view for every such rule. A future table or recording profile could legitimately validate a file years before anyone can safely subset it. The generic interpreter also supplies MRI and behavioural filenames as its default editable companions. The archive interpreter’s identity includes the BIDS library fingerprint and a repository fingerprint that covers processing-runner sources. An unrelated runner change can therefore change an archive’s new interpretation fingerprint and require an extra read when editing it. The existing comparison can absorb a fingerprint-only change when the recorded meaning agrees. [Modality rules](../modules/bids/src/main/scala/sanctity/bids/ModalityRules.scala#L8) · [Service assembly](../modules/service/src/main/scala/sanctity/app/ApiServer.scala#L31) · [Generic interpreter](../modules/application/src/main/scala/sanctity/application/Capabilities.scala#L50) · [Fingerprint inputs](../build.sbt#L53)

**Design change.** Keep compile-time registration. Let each profile declare which operations it supports, with separate capabilities for assessment, editing and view preparation. Make the packaged service report those capabilities to clients. Add one test profile that assesses a file and has no editor or view. When narrowing semantic fingerprints, preserve old encodings and use the compatibility corpus. This gives the next real modality an extension path without introducing a plugin framework.

**A practical interoperability test for the next profile.** Participant fields currently retain their written values, and selection hits identify their release. But participant predicates use field names, and files under `phenotype/` currently receive preservation coverage. Two labs might both call a column `score` while using different instruments or scoring versions. Carry the source table, dictionary, units, coded values and missing-value rules with a versioned release. Keep participant labels scoped to their dataset. Test that an independent reader can distinguish two definitions of `score` and two different people called `sub-01`. Combining variables should require an explicit mapping. This is the valuable part of the planned table work even with no capture-system connector. [Query model](../modules/kernel/src/main/scala/sanctity/kernel/Query.scala#L10) · [Participant parsing](../modules/bids/src/main/scala/sanctity/bids/ParticipantTable.scala#L36) · [Preserved directories](../modules/bids/src/main/scala/sanctity/bids/BidsScopes.scala#L29) · [Table plan](build-plan.md)

**Related defect, reproduced.** The dataset interpreter describes a change from archive to BIDS as an ordinary new release. I prepared a valid BIDS manifest against an accepted archive using the application draft interface. Preparation required reassessment. After I reassessed and accepted the original archive, retrying against its new head gave the same result. The guard compares the reread base *with the target profile*. Ordinary browser uploads also merge additions and named replacements, so they cannot remove the obsolete root descriptor. My recommended default is to keep the deposited archive intact and admit the curated BIDS collection as a linked result. If same-dataset conversion is a product requirement, give it an explicit reviewed transition. Either choice should yield a truthful result instead of a circular instruction. [Declared behavior](../modules/bids/src/main/scala/sanctity/bids/DatasetInterpreter.scala#L10) · [Reassessment guard](../modules/application/src/main/scala/sanctity/application/NativeRepository.scala#L162)

### 7. Qualify archival recovery and external guests together with their policy

The independent recovery workflow verifies content and policy history before reopening access. It currently refuses an inventory containing a non-local eligibility record or a quarantined or withdrawn dataset or release. This is an intentional, explicit boundary. A successful two-lab login and revocation is evidence for shared-installation collaboration. It does not qualify recovery of a sponsored external guest, withdrawal after backup, or loss of the physical host. A future storage adapter also needs a recovery implementation: the live byte-store port is small, while backup and verification directly use the filesystem object layout. [Recovery checks](../modules/postgres/src/main/scala/sanctity/postgres/OrganizationRecovery.scala#L177) · [Backup inventory](../modules/postgres/src/main/scala/sanctity/postgres/BackupBundle.scala#L113) · [Rehearsal scope](organization-recovery.md)

**Pilot gate.** Choose a specific institution, custodian, retention policy and independent backup destination. Demonstrate a replacement host serving exact permitted bytes, while a collaborator whose access ended stays excluded and a withdrawn release remains unavailable. Record the recovery point, elapsed recovery time and operator actions. A portable exchange copy and an operator backup have different disclosure and recovery requirements.

## Recommended order

1. **Finish one deposit-to-discovery journey.** Give custody a name, index the small release catalog record, fix paging, expose discoverable sharing, and show server-backed grants. Keep the existing admission, current-authority and scientific-query paths. The exit is a researcher finding a years-old collection from Home, without a UUID or help from its original curator.
2. **Make that journey usable by an independent client.** Close the OpenAPI drift, exercise retries and expiry, and implement the smallest offline exchange receipt. The exit is a second empty repository verifying the disclosed inventory and accepting its own copy with independent custody. Exercise a fixed release and a restricted view.
3. **Prove the institutional operating envelope.** Start measuring the policy path during the first tranche. Qualify scoped authorization, realistic file sizes, recovery and lifecycle behavior before making a production archival commitment. Decouple profile capabilities when adding the next real data type.

The roadmap can stay centered on one repository, one acceptance workflow, one current-authority decision and ordinary files at its boundary. New integrations can then be independently developed and tested against that boundary.

## Verification

Fresh `sbt check` passed **674 tests**. Four focused PostgreSQL suites passed **35 tests** on a disposable PostgreSQL 17 instance: coverage persistence, disclosure, organization HTTP and repository HTTP. Three temporary Scala probes exercised cross-catalog export/import, kind change after reassessment and directory rename between pages. The two GET-only probes against the seeded packaged service checked archive discovery and the actual release response. The route count was obtained by normalizing path parameters and comparing method/path pairs.

The full PostgreSQL suite, crash/restore rehearsal, off-host recovery and institution-scale workload were not rerun for this review. Historical evidence is identified above. The priority order, transfer format and suggested handling of archive-to-BIDS conversion are design recommendations. The review changed no application behavior.
